## Introduction

The **Schreier–Sims algorithm** is an algorithm in computational group theory, named after the mathematicians Otto Schreier and Charles Sims. It solves many problems in polynomial time, such as finding the order of a finite permutation group or checking whether a given permutation belongs to a given group. Sims first introduced the Schreier–Sims algorithm in 1970, based on Schreier's lemma. In 1981[^knuth-year], Donald Knuth further improved its running time. Later, a faster randomized version of the algorithm was developed. Computer algebra systems (such as GAP and Magma) usually use a highly optimized Monte Carlo version of the algorithm[^monte-carlo].

???+ info "Notation"
    Following the convention of the computational group theory literature, this article writes group actions as right actions, which means permutations are composed from left to right. All group actions in this article can be viewed as permutation actions, although some of the algorithms also work for more general group actions. Accordingly, the set acted on is $X=\{1,2,\cdots,n\}$ by default, and its elements are called points. The result of a permutation $g$ acting on a point $x$ is written $x^g$; we also say the permutation $g$ moves the point $x$ to the point $x^g$. Finally, under the action of a permutation group $G$, the orbit of a point $x$ is written $x^G=\{x^g:g\in G\}$, and its stabilizer is written $G_x=\{g\in G:x^g=x\}$. The notion of a stabilizer extends to a set $B\subseteq X$, whose (pointwise) stabilizer is defined as $G_B=\bigcap_{x\in B}G_x$.

## Overview

The Schreier–Sims algorithm mainly tries to solve the following problem:

-   Given a set $S$ of permutations on a set $X$ of size $n$, how can we efficiently store the permutation group $G=\langle S\rangle$ generated by $S$ on a computer, and answer a series of queries about this group?

Clearly, such a group $G$ can be very large, far larger than the set $X$ and the generating set $S$. For example, the symmetric group of degree $n$, $S_n=\langle(123\cdots n),(12)\rangle$, has size $n!$, yet it can be generated by just two permutations. Storing every element of the group is not realistic.

Similar to using [Gaussian elimination](../numerical/gauss.md) to build a [basis](../linear-algebra/basis.md) of a vector space, the idea of the Schreier–Sims algorithm is to find a kind of "basis" for a finite permutation group $G$:

1.  The input of the algorithm is a generating set $S$ of $G$, consisting of some permutations;
2.  If the group $G$ is not trivial, we can always find a point $\beta$ that is moved by the action of $G$, that is, $|\beta^G|>1$;
3.  Find the orbit $\Delta=\beta^{G}$ of the point $\beta$, and for each point $\delta\in\Delta$ of the orbit, find a permutation $t_{\delta}$ in $G$ that moves $\beta$ to $\delta$;
4.  Find a generating set $S'$ of the stabilizer $G_{\beta}$ of the point $\beta$;
5.  Recursively run the algorithm on $G'=\langle S'\rangle$, until we reach the trivial group $\{e\}$.

This idea works because the stabilizer $G_{\beta}$ of the point $\beta$ is a subgroup of $G$. All of its (right) cosets form a partition of $G$, and these cosets are in one-to-one correspondence with the orbit $\beta^G$ of $\beta$. The permutations $t_{\delta}$ found in step 3 are exactly representatives of these cosets. This set $T$ of coset representatives is called a **transversal** of the stabilizer $G_{\beta}$. In other words, every element $g$ of $G$ corresponds to a unique pair $(h,t)\in G_\beta\times T$ with $g=ht$. So, as long as we can store the subgroup $G_{\beta}$ and the corresponding transversal $T$, we can store the whole group $G$. And storing the subgroup $G_{\beta}$ is already solved: just call the algorithm recursively.

Of course, there are many implementation details to work out, and that is the main content of this article. But before that, let us look at what the algorithm produces: what structure it stores the group in, and what queries this structure can answer. For this, we need a few concepts.

### Stabilizer chain

Suppose the algorithm is run on the group $G=\langle S\rangle$ a total of $k$ times. In the $i$-th call, the input is the set of permutations $S^{(i-1)}$, the point found is $\beta_i$, the transversal obtained is $T_i$, and the generating set obtained for the stabilizer is $S^{(i)}$. If we write $G^{(i)}=\langle S^{(i)}\rangle$, then the algorithm actually produces the chain of subgroups

$$
G=G^{(0)}> G^{(1)}>\cdots> G^{(k-1)}> G^{(k)}=\{e\}.
$$

Moreover, every subgroup in the chain is a stabilizer

$$
G^{(i)}=G_{\beta_1,\cdots,\beta_i}.
$$

So the Schreier–Sims algorithm can be seen as computing such a **stabilizer chain**.

### Base and strong generating set

If a subset $B$ of $X$ satisfies $G_B=\{e\}$, then $B$ is called a **base** of the permutation group $G$. Clearly, the algorithm above produces a base $B=\{\beta_1,\cdots,\beta_k\}$. This means that the images of these points under a permutation $g\in G$ uniquely determine that permutation within $G$. Moreover, the base output by the algorithm also satisfies

$$
G^{(i-1)}=G_{\beta_1,\cdots,\beta_{i-1}}>G_{\beta_1,\cdots,\beta_{i-1},\beta_i}=G^{(i)}.
$$

That is, every point in the base carries useful information about the elements of the group. Such a base is called **nonredundant**. The algorithm always outputs a nonredundant base. The stabilizer chain of such a base is strictly decreasing.

At the same time, the union of the generating sets obtained by the algorithm

$$
\bar S=\bigcup_{i=0}^kS^{(i)}
$$

is also a generating set of $G$, and it satisfies $\langle\bar S\cap G^{(i)}\rangle = G^{(i)}$. A generating set with this property is called a **strong generating set** of $G$ relative to the base $B$. So the Schreier–Sims algorithm can also be seen as computing a **base and strong generating set** (BSGS) of $G$. This is equivalent to talking about the stabilizer chain, and this article does not distinguish between the two.

Of course, the algorithm also produces a series of orbits $\Delta_i=\beta_{i}^{G^{(i-1)}}$ and the corresponding transversals $T_i$. These orbits are called the **basic orbits** of $G$. Whenever this article mentions the stabilizer chain or the base and strong generating set of $G$, it assumes that the corresponding basic orbits and transversals have also been computed.

### Data structure

This article gives a number of pseudocode listings. In the pseudocode, the stabilizer chain (or base and strong generating set) of a group is stored in a data structure $C$:

$$
C=(S,\Delta,T,C').
$$

The data members of this structure are the generating set $S$ of the current group, the basic orbit $\Delta$, the corresponding transversal $T$, and the stabilizer $C'$, stored as a nested substructure. Of course, the stabilizer $C'$ is also such a structure. The whole group is actually stored in a layered structure, where each layer describes one group in the stabilizer chain. The innermost layer is an empty structure, representing $G^{(k)}=\{e\}$.

In the pseudocode, the members of this data structure are accessed as $C.generators$, $C.orbit$, $C.transversal$ and $C.next$. The first element of the orbit, $C.orbit[0]$, is assumed to be the base point $\beta$, and the corresponding coset representative $C.transversal[\beta]$ is assumed to be the identity $e$. Note that although we access the elements of the orbit and the transversal with array indices here, they need not be stored as arrays. Read this as saying that they provide a way to get the first element of the orbit and to look up the coset representative for a point in the orbit. Implementation details are discussed below.

### Applications

Once we have a base and strong generating set of a group, we can answer a range of queries about the group. The most basic ones, and the ones most often seen in competitive programming, are finding the order of the group and checking whether a permutation belongs to the given group.

#### Order of a group

If a base and strong generating set of $G$ is known, then by Lagrange's theorem and the orbit-stabilizer theorem, the order of $G$ can be computed as

$$
|G|=\prod_{i=1}^k[G^{(i-1)}:G^{(i)}]=\prod_{i=1}^k[G^{(i-1)}:G^{(i-1)}_{\beta_i}]=\prod_{i=1}^k|T_i|.
$$

So multiplying the sizes of all transversals $T_i$ (or, equivalently, the lengths of the basic orbits $\Delta_i$) gives the order of $G$.

#### Membership testing

Given a base and strong generating set of $G$, we can also decide whether a permutation $h$ belongs to $G$. This is called the **membership testing** problem.

This problem can be solved recursively. To decide whether $h\in G^{(i-1)}$, first find the representative $t\in T_i$ of the coset of $G^{(i)}$ that contains $h$. If it exists, let $h'=ht^{-1}$; then $h=h't$, and $h\in G^{(i-1)}$ is equivalent to $h'\in G^{(i)}$, so the problem becomes deciding whether $h'\in G^{(i)}$. If no such $t$ exists, or we have recursed down to $G^{(k)}=\{e\}$ but $h\neq e$, we conclude that $h\notin G$. In fact, this process not only decides whether $h\in G$; when $h\in G$, it also writes $h$ as a product of coset representatives $t_k\cdots t_2t_1$ with $t_i\in T_i$. For elements of $G$, such a representation exists and is unique. This again shows that the formula for the order of the group above is correct.

Here is the process as pseudocode:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{MembershipTest}(C,h):\\
\textbf{Input. }\textrm{A stabilizer chain }C\textrm{ for a group }G\textrm{ and a permutation }h.\\
\textbf{Output. }\textrm{Whether }h\in G.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \textbf{while }C\textrm{ is not empty }\\
2  & \qquad \beta \leftarrow C.orbit[0]\\
3  & \qquad \delta \leftarrow \beta^h\\
4  & \qquad \textbf{if }\delta\in C.orbit\textbf{ then}\\
5  & \qquad \qquad t \leftarrow C.transversal[\delta]\\
6  & \qquad \qquad h \leftarrow ht^{-1}\\
7  & \qquad \textbf{else }\\
8  & \qquad \qquad \textbf{return }\textrm{false}\\
9  & \qquad \textbf{end if}\\
10 & \qquad C \leftarrow C.next\\
11 & \textbf{end while}\\
12 & \textbf{return }h=e
\end{array}
\end{array}
$$

As we will see below, membership testing is also an important part of the implementation of the Schreier–Sims algorithm discussed in this article.

## Computing orbits, transversals and stabilizers

To implement the Schreier–Sims algorithm, we first need to solve the following subproblem:[^orbit-algo]

-   Given a generating set $S$ of a group $G$ and a point $\beta$, how do we find the orbit $\beta^G$, the corresponding transversal $T$, and a generating set of the stabilizer $G_\beta$?

This is the problem this section solves.

### Storing orbits and transversals

To find the orbit and the transversal, a direct search is enough. The pseudocode is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{OrbitTransversal}(S,\beta):\\
\textbf{Input. }\textrm{A generating set }S\textrm{ for a group }G\textrm{ and a point }\beta.\\
\textbf{Output. }\textrm{The orbit }\Delta=\beta^G\textrm{ and the transversal }T.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \Delta \leftarrow [\beta]\\
2  & T[\beta] \leftarrow e\\
3  & \textbf{for }\delta\in\Delta\\
4  & \qquad \textbf{for }s\in S\\
5  & \qquad \qquad \gamma \leftarrow \delta^s\\
6  & \qquad \qquad \textbf{if }\gamma\notin\Delta\textbf{ then}\\
7  & \qquad \qquad \qquad\textrm{append }\gamma\textrm{ to }\Delta\\
8  & \qquad \qquad \qquad T[\gamma] \leftarrow T[\delta]\cdot s\\
9  & \qquad \qquad \textbf{end if}\\
10 & \qquad \textbf{end for}\\
11 & \textbf{end for}\\
12 & \textbf{return }\Delta, T
\end{array}
\end{array}
$$

In an implementation, either breadth-first search or depth-first search works. The search visits $|S||T|$ states, so as long as the orbit and transversal are stored sensibly, the time complexity is perfectly acceptable.

For permutation groups, an orbit is just a set of at most $n$ points. To make lookup and insertion efficient, it can be stored as a Boolean array or an unordered set. Both operations then take $O(1)$ time, and the total space used is $O(n)$. Of course, depending on how the transversal is implemented, you may also need to record the position of the first element separately.

The question is what data structure to use to store the corresponding transversal $T$.

#### Direct storage

The simplest method, of course, is to store every element $t$ of the transversal $T$ directly. A single permutation stored in [one-line notation](../permutation.md#单行记号) takes exactly $n$ space, so storing such a transversal takes $O(|T|n)$ space. The advantage is that accessing a single coset representative takes $O(1)$ time; the cost is that computing these coset representatives the first time takes $O(|T|n)$ time.

#### Schreier tree

Another common approach is to store the transversal in a tree structure. It is called a **Schreier tree** or **Schreier vector**[^schreier-vector]. Its root is $\beta$, and its vertices are the elements $\delta$ of the orbit $\Delta$. Each time the search finds a new vertex $\gamma=\delta^s$, we add an edge from the old vertex $\delta$ to the new vertex $\gamma$, and record on the edge the index (or a pointer) of the permutation $s$ in the generating set $S$. Since the generating set is already stored, the extra space for the transversal is $O(|T|)$. When $n$ is very large, this saves a lot of space, and the first computation takes $O(|T|)$ time. The side effect is that every time we need a coset representative, we must walk along the edges on the path from the vertex to the root and recompute it, so the time complexity depends heavily on the depth of the Schreier tree. In general, the depth of the tree can reach $O(n)$.

In an implementation, you need to balance the time and space complexity according to the actual situation. In competitive programming, $n$ is usually small and memory is plentiful, while time is often the bottleneck. As we will see later, the most expensive step of the Schreier–Sims algorithm accesses coset representatives many times, so direct storage is often better. But in some applications $n$ may be large and memory may be tighter, and then you may need to store the transversal as a Schreier tree. For this case, to keep the Schreier tree from getting too deep, researchers have proposed many methods that rebuild a shallow Schreier tree when the tree becomes too deep. Interested readers can consult the references at the end.

In the pseudocode, this article does not distinguish between implementations of the transversal. It only assumes that the data structure storing the transversal $T$ supports reading and modifying the coset representative $T[\delta]$ for an orbit element $\delta\in\Delta$.

### Schreier's lemma

Once we have the orbit $\beta^G$ and the transversal $T$, Schreier's lemma gives a way to get a generating set of the stabilizer $G_\beta$.

???+ note "Schreier's lemma"
    Let the group $G=\langle S\rangle$ have a subgroup $H\le G$. Let $T$ be a (right) transversal of the subgroup $H$ with $e\in T$[^schreier-lemma-unity], and for $g\in G$ write $\overline g$ for the representative $t\in T$ of the coset containing $g$. Then the set
    
    $$
    U=\{ts(\overline{ts})^{-1}:t\in T,s\in S\}
    $$
    
    is a generating set of the subgroup $H$. Its elements are called the **Schreier generators** of the subgroup $H$.

??? note "Proof"
    First, by the definition of coset representatives, $ts(\overline{ts})^{-1}\in H$ for all $t\in T,s\in S$, so $\langle U\rangle\subseteq H$.
    
    Conversely, for any $h\in H$, since $S$ is a generating set of $G\ge H$, there must be a sequence $s_i\in S\cup S^{-1}$ such that
    
    $$
    h=s_1s_2\cdots s_r
    $$
    
    holds. Let $t_1=e$ and recursively define $t_{i+1}=\overline{t_is_i}\in T$. Then
    
    $$
    \begin{aligned}
    h&=\left(t_1s_1t_2^{-1}\right)\left(t_2s_2t_3^{-1}\right)\cdots\left(t_rs_rt_{r+1}^{-1}\right)t_{r+1}.
    \end{aligned}
    $$
    
    For each $i=1,2,\cdots,r$ we have $t_is_it_{i+1}^{-1}=t_is_i(\overline{t_is_i})^{-1}\in U\cup U^{-1}\subseteq H$, so $t_{r+1}\in H$. But $H\cap T=\{e\}$, so $t_{r+1}=e$. This shows that every $h\in H$ can be written as a product of a sequence of $u_i=t_is_it_{i+1}^{-1}\in U\cup U^{-1}$, that is, $U$ generates $H$.

Since the subgroup corresponding to the transversal $T$ is exactly the stabilizer $G_\beta$, once we have the transversal $T$, combining it with the generating set $S$ of $G$ gives a generating set of the stabilizer $G_\beta$.

### Algorithm

With a small change to the pseudocode above, we can get a generating set of the corresponding stabilizer while computing the orbit and the transversal:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{OrbitTransversalStabilizer}(S,\beta):\\
\textbf{Input. }\textrm{A generating set }S\textrm{ for a group }G\textrm{ and a point }\beta.\\
\textbf{Output. }\textrm{The orbit }\Delta=\beta^G\textrm{, the transversal }T\textrm{, and a}\\
\qquad\textrm{ generating set }S'\textrm{ for the stabilizer }G_\beta.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \Delta \leftarrow [\beta]\\
2  & T[\beta] \leftarrow e\\
3  & S' \leftarrow [e]\\
4  & \textbf{for }\delta\in\Delta\\
5  & \qquad \textbf{for }s\in S\\
6  & \qquad \qquad \gamma \leftarrow \delta^s\\
7  & \qquad \qquad \textbf{if }\gamma\notin\Delta\textbf{ then}\\
8  & \qquad \qquad \qquad\textrm{append }\gamma\textrm{ to }\Delta\\
9  & \qquad \qquad \qquad T[\gamma] \leftarrow T[\delta]\cdot s\\
10 & \qquad \qquad \textbf{else} \\
11 & \qquad \qquad \qquad \textrm{append }T[\delta]\cdot s\cdot T[\gamma]^{-1}\textrm{ to }S'\\
12 & \qquad \qquad \textbf{end if}\\
13 & \qquad \textbf{end for}\\
14 & \textbf{end for}\\
15 & \textbf{return }\Delta, T, S'
\end{array}
\end{array}
$$

In the pseudocode, for each pair $(\delta,s)$, $t_\delta st_{\delta^s}^{-1}$ is a new Schreier generator only when it does not produce a new element of the orbit; otherwise, it is the identity $e$. So the algorithm actually produces at most

$$
|S||T|-(|T|-1) = (|S|-1)|T|+1
$$

Schreier generators (not counting the initial identity). In general, this upper bound is tight[^upper-bound]. But for the finite groups we actually deal with, the bound is very loose: most of the newly produced Schreier generators are duplicates of earlier ones, or can be composed from earlier generators.

Since the basic flow of the Schreier–Sims algorithm can be implemented by recursively calling the algorithm above for computing orbits and stabilizers, we already have a naive implementation of the Schreier–Sims algorithm at this point. But without filtering, the number of Schreier generators grows exponentially: applying $|S^{(i)}|=O(|S^{(i-1)}||T_i|)$ repeatedly shows that the generating set of the innermost stabilizer would have size $O(|S||G|)$. This is absurdly inefficient, since the innermost stabilizer is $\{e\}$.

Sims's work gave a way to limit the growth of the number of Schreier generators. It guarantees that the final strong generating set $\bar S$ has size $O(n^2)$. This makes it possible to compute a base and strong generating set in polynomial time.

## The Schreier–Sims algorithm

To solve the problem above, this section discusses an incremental implementation of the Schreier–Sims algorithm whose strong generating set has size $O(n^2)$.

### Sifting

The core optimization of the Schreier–Sims algorithm over the naive algorithm above is very simple: before adding any Schreier generator to the generating set of the stabilizer, it must first go through **sifting**. Sifting means first checking whether the new Schreier generator already lies in the subgroup generated by the existing generators, and only adding generators that do not. For this, we just use the membership testing algorithm $\textrm{MembershipTest}(C,h)$ from earlier.

But this only works if the stabilizer chain (or base and strong generating set) of the group generated by the Schreier generators produced so far for the current group has already been built. This means that every time we add a new Schreier generator to the generating set of the stabilizer, we must dynamically maintain the inner stabilizer chain, to use it for later sifting. However, each generator inserted into the current layer may produce several Schreier generators, which may update the inner structure several times; and each update of the inner structure may in turn trigger several updates of structures further inside.

It seems the exponential blow-up mentioned earlier is still there. In fact it is not. Because sifting is done first, a layer is updated only when the generator to be added really enlarges that layer. So the number of updates to a single layer equals the number of times the group stored in that layer strictly grows. But a chain of subgroups of a group of size $|G|$ has length at most $\log_2|G|$, because Lagrange's theorem guarantees that each extra step in the chain at least doubles the size of the group. So a single layer is updated at most $\log_2|G|$ times, and the final strong generating set $\bar S$ has size $O(|B|\log|G|)$.

This estimate can be improved further. Since the group $G$ here is known to be a subgroup of the symmetric group $S_n$ of degree $n$, the length of a subgroup chain of $G$ cannot exceed that of $S_n$. It can be shown[^subgroup-chain] that a strictly increasing chain of subgroups of $S_n$ has length at most $3n/2$. So the number of updates of a single layer is actually $O(n)$. Clearly, the base also has size at most $n$. Therefore, the final strong generating set $\bar S$ has size $O(n^2)$.

The sifting method described here was proposed by Sims and is also called the Sims filter. There is a more complex sifting method proposed by Jerrum, called the [Jerrum filter](https://groupprops.subwiki.org/w/index.php?title=Jerrum%27s_filter), which guarantees a strong generating set of size $O(n)$. Interested readers can study it on their own.

A small optimization for sifting: in the implementation of $\textrm{MembershipTest}(C,h)$, instead of returning a Boolean, return the final "siftee"[^siftee] $h$ (that is, replace lines $8$ and $12$ of the pseudocode with $\textbf{return }h$). If the siftee $h\neq e$, the membership test failed, and we can add the siftee $h$ to the current layer instead of the original $h$. The siftee $h$ has already had several coset representative factors removed, so it moves fewer points, which reduces the local amount of computation. This optimization does not affect the overall complexity at all.

### Process

Now we can describe the Schreier–Sims algorithm in detail: first, initialize an empty structure $C$ to store the stabilizer chain of the group. Then add the generators in the generating set $S$ to $C$ one by one. The final structure $C$ is the stabilizer chain of the group $\langle S\rangle$. The pseudocode is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{SchreierSims}(S):\\
\textbf{Input. }\textrm{A generating set }S\textrm{ for a group }G.\\
\textbf{Output. }\textrm{The stabilizer chain }C\textrm{ for the group }G.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & C \leftarrow []\\
2  & \textbf{for }s\in S\\
3  & \qquad C \leftarrow \textrm{Extend}(C,s)\\
4  & \textbf{end for}\\
5  & \textbf{return }C
\end{array}
\end{array}
$$

The core of the algorithm is the step that adds a new generator $s$ to the current $C$, that is, the subroutine $\textrm{Extend}(C,s)$. As described above, $C$ must be a stabilizer chain both before and after adding the permutation $s$. So before adding $s$, we can sift it first. If $s$ turns out not to be in the existing group, we compute the orbit, the coset representatives and the Schreier generators **incrementally**. "Incrementally" here means that anything already computed is not recomputed. This is what guarantees the correct complexity.

Let us see how to turn $\textrm{OrbitTransversalStabilizer}(S,\beta)$ into an incremental version. The algorithm searches the state space $\Delta\times S$. After adding a new generator $s$, the state space becomes $\Delta'\times\left(S\cup\{s\}\right)$. The difference between the two is

$$
\left(\Delta\times\{s\}\right)\cup\left((\Delta'\setminus\Delta)\times \left(S\cup\{s\}\right)\right).
$$

This means that when a new generator $s$ is added, we first combine the new generator $s$ with the old orbit and its coset representatives. If this produces new elements of the orbit, we then combine these elements with all generators (old and new). This repeats until the orbit stops growing.

The pseudocode for adding a permutation $g$ to the structure $C$ is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{Extend}(C,g):\\
\textbf{Input. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\textrm{ and a}\\
\qquad \textrm{permutation }g.\\
\textbf{Output. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\cup\{g\}.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \textbf{if }\textrm{MembershipTest}(C,g)\textrm{ is passed}\textbf{ then}\\
2  & \qquad \textbf{return }C\\
3  & \textbf{end if}\\
4  & \textbf{if }C\textrm{ is empty}\textbf{ then}\\
5  & \qquad \beta \leftarrow \textrm{an element moved by }g\\
6  & \qquad C.orbit[0] \leftarrow \beta \\
7  & \qquad C.transversal[\beta] \leftarrow e\\
8  & \textbf{end if}\\
9  & \textrm{append }g\textrm{ to }C.generators\\
10 & \Delta \leftarrow \textrm{a copy of }C.orbit \\
11 & \textbf{for }\delta\in\Delta \\
12 & \qquad \gamma \leftarrow \delta^g \\
13 & \qquad \textbf{if }\gamma\notin C.orbit\textbf{ then}\\
14 & \qquad \qquad \textrm{append }\gamma\textrm{ to }C.orbit\\
15 & \qquad \qquad C.transversal[\gamma] \leftarrow C.transversal[\delta]\cdot g\\
16 & \qquad \textbf{else}\\
17 & \qquad \qquad s'\leftarrow C.transversal[\delta]\cdot g\cdot C.transversal[\gamma]^{-1}\\
18 & \qquad \qquad C.next \leftarrow \textrm{Extend}(C.next, s')\\
19 & \qquad \textbf{end if}\\
20 & \textbf{end for} \\
21 & \textbf{for }\delta\in C.orbit\setminus\Delta \\ 
22 & \qquad \textbf{for }s\in C.generators \\
23 & \qquad \qquad \gamma \leftarrow \delta^s \\
24 & \qquad \qquad \textbf{if }\gamma\notin C.orbit\textbf{ then}\\
25 & \qquad \qquad \qquad \textrm{append }\gamma\textrm{ to }C.orbit\\
26 & \qquad \qquad \qquad C.transversal[\gamma] \leftarrow C.transversal[\delta]\cdot s\\
27 & \qquad \qquad \textbf{else}\\
28 & \qquad \qquad \qquad s'\leftarrow C.transversal[\delta]\cdot s\cdot C.transversal[\gamma]^{-1}\\
29 & \qquad \qquad \qquad C.next \leftarrow \textrm{Extend}(C.next, s')\\
30 & \qquad \qquad \textbf{end if}\\
31 & \qquad \textbf{end for}\\
32 & \textbf{end for} \\
33 & \textbf{return }C
\end{array}
\end{array}
$$

This gives the complete Schreier–Sims algorithm.

### Another implementation

The implementation above is already correct, but lines $12\sim 19$ and $23\sim 30$ are somewhat repetitive. Based on this, Knuth proposed a simpler recursive implementation in his paper. His approach treats this repeated part as an update of the transversal (and the orbit). Every update of the transversal must be combined with all generators, and depending on whether a new coset representative is produced, it either calls itself recursively or calls the routine that adds a generator. The pseudocode is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{Extend}(C,g):\\
\textbf{Input. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\textrm{ and a}\\
\qquad \textrm{permutation }g.\\
\textbf{Output. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\cup\{g\}.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \textbf{if }\textrm{MembershipTest}(C,g)\textrm{ is passed}\textbf{ then}\\
2  & \qquad \textbf{return }C\\
3  & \textbf{end if}\\
4  & \textbf{if }C\textrm{ is empty}\textbf{ then}\\
5  & \qquad \beta \leftarrow \textrm{an element moved by }g\\
6  & \qquad C.orbit[0] \leftarrow \beta \\
7  & \qquad C.transversal[\beta] \leftarrow e\\
8  & \textbf{end if}\\
9  & \textrm{append }g\textrm{ to }C.generators\\
10 & \textbf{for }t\in\textrm{a copy of }C.transversal\\
11 & \qquad \textrm{ExtendTransversal}(C,t\cdot g)\\
12 & \textbf{end for}\\
13 & \textbf{return }C
\end{array}\\
\\
\textbf{Sub-Algorithm }\textrm{ExtendTransversal}(C,t):\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \beta \leftarrow C.orbit[0]\\
2  & \gamma \leftarrow \beta^t\\
3  & \textbf{if }\gamma\notin C.orbit\textbf{ then}\\
4  & \qquad \textrm{append }\gamma\textrm{ to }C.orbit\\
5  & \qquad C.transversal[\gamma] \leftarrow t\\
6  & \qquad \textbf{for }s\in C.generators\\
7  & \qquad \qquad \textrm{ExtendTransversal}(C,t\cdot s)\\
8  & \qquad \textbf{end for}\\
9  & \textbf{else}\\
10 & \qquad s' \leftarrow t\cdot C.transversal[\gamma]^{-1}\\
11 & \qquad C.next \leftarrow \textrm{Extend}(C.next,s')\\
12 & \textbf{end if}
\end{array}
\end{array}
$$

Comparing this pseudocode with the one in the previous section shows that it is correct, and the two have the same complexity. Note that line $10$ of $\textrm{Extend}$ iterates over the transversal as it was when entering the loop: the coset representatives newly produced inside the loop have already been combined with all generators in the recursion of $\textrm{ExtendTransversal}$, and should not be visited again.

### Complexity

To analyze the complexity of the Schreier–Sims algorithm, we need some notation. Let the permutations have length $n$ and the generating set have size $|S|=m$. Let $|B|$ be the length of the resulting (nonredundant) base. In the final structure, for the stabilizer $G^{(i-1)}$ in the $i$-th layer from the outside, let $|S^{(i-1)}|$ be the number of its generators, and $|T_i|$ the size of its transversal (or the length of its orbit). Below we analyze the time complexity of the incremental implementation of the Schreier–Sims algorithm above. The algorithm has two main parts: sifting, and computing the orbits, transversals and Schreier generators.

Both the initial input generators and the Schreier generators produced by the algorithm must be sifted, so sifting is performed $O(\sum_{i=1}^{|B|}|S^{(i-1)}||T_i|+|S|)$ times in total. A single sift computes permutation products with $O(|B|)$ coset representatives. Let $\tau$ be the time to compute the product with a single coset representative. With direct storage of coset representatives, $\tau\in O(n)$; with a Schreier tree, $\tau\in O(n^2)$. The total time for sifting is $O(\tau|B|\sum_{i=1}^{|B|}|S^{(i-1)}||T_i|+\tau|B||S|)$.

For computing orbits and related information, since the implementation is incremental, each pair $(\delta,s)\in\Delta_i\times S^{(i-1)}$ in the state space is processed at most once. For orbits and transversals, depending on the storage method, computing a single coset representative takes $O(n)$ or $O(1)$ time. In any case, this does not exceed the cost of computing a Schreier generator, which is $O(n)$ with direct storage and $O(n^2)$ with a Schreier tree. Comparing with the total time for sifting, we see that computing this information never takes more time than sifting. So the time complexity of the Schreier–Sims algorithm is the $O(\tau|B|\sum_{i=1}^{|B|}|S^{(i-1)}||T_i|+\tau|B||S|)$ from the previous paragraph.

As for space, the final data structure stores $O(\sum_{i=1}^{|B|}|S^{(i-1)}|)$ generators and $O(\sum_{i=1}^{|B|}|T_i|)$ coset representatives. With direct storage, both generators and coset representatives take $O(n)$ space each; with a Schreier tree, generators take $O(n)$ space and coset representatives only $O(1)$.

As shown earlier, a strictly increasing chain of subgroups of the symmetric group of degree $n$ has length $O(n)$, which applies to both $|B|$ and $|S^{(i)}|$. So the Schreier–Sims algorithm with direct storage of transversals runs in $O(n^5+mn^2)$ time and $O(n^3)$ space. Of course, when $\log|G|\in O(n)$, a better estimate is $O(n^2\log^3|G|+mn\log|G|)$ time[^knuth-complexity] and $O(n^2\log|G|)$ space. For random generating sets, experiments show that the algorithm runs noticeably faster than $\Theta(n^5)$, roughly in $\Theta(n^4)$.

Compared with direct storage, a Schreier tree adds an extra factor of $n$ to the time complexity. But when $n$ is large and the group itself is much smaller than the symmetric group of degree $n$, its space complexity is $O(n\log^2|G|)$, far less than the $O(n^2\log|G|)$ of direct storage. In competitive programming, however, it is hard to find cases where storing a Schreier tree is better.

### Reference implementation

Here is a reference implementation of the Schreier–Sims algorithm. Since $n$ is small, the implementation fixes the base as $B=\{n,n-1,\cdots,1\}$ instead of letting the algorithm choose it. The benefit is that the permutations in the group at the $k$-th layer from the inside (not counting the empty structure) only change the first $k$ elements, which makes later computations easier. Another optimization in the code is that, when storing a coset representative, it actually stores its inverse permutation, which simplifies the permutation arithmetic.
